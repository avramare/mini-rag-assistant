# Decisions

One line per decision, with the reason. Newest at the bottom.

1. **Filter by access before ranking, not after top-k.** Otherwise restricted docs can take the top-k slots and a cleared-for-less user gets fewer (or zero) results, and a bug in the post-filter leaks.
2. **Invalid model output gets exactly one retry, recorded on the result.** Evals must be able to count format failures; unlimited retries would hide them.
3. **Citations outside the retrieved set are an error (`invalid_citation`).** A citation the user was never shown is either hallucinated or a leak.
4. **A non-refused answer with no citations is turned into a refusal (`refusal_reason="uncited"`).** An ungrounded answer must not reach the user, but the reason is kept so evals can count it apart from model refusals.
5. **Old and new versions of a policy coexist as separate docs with unique ids and an `effective` date.** Tests whether the model picks the current version; ids stay unique because citations and access control key on them.
6. **"Current" means latest effective date not after today; today is injected, not read from the clock.** A future-dated doc (Orion v2, 2027-01-01) is an "announced, not in force" trap; tests pin the date so they stay deterministic.
7. **`num_ctx` is sent explicitly on every Ollama call (default 4096, from `.env`).** Ollama silently truncates the start of an over-long prompt, dropping system rules and context without an error.
8. **Record `prompt_eval_count` and flag `truncation_risk` above `MAX_PROMPT_CTX_SHARE` (0.75) of `num_ctx`.** The real token count is the only runtime signal that a prompt is close to being truncated.
9. **Static worst-case prompt estimate uses chars/3.** English is ~4 chars/token, so /3 overestimates on purpose; a check that is too generous is worse than one that is slightly strict.
10. **Thinking is disabled only for models that report the `thinking` capability.** Thinking tokens cost time and are not part of the answer contract; sending `think` to other models is an error.
11. **Structured outputs with the `Answer` JSON schema (`additionalProperties: false`).** Constrained decoding cuts format failures at the source; validation with pydantic still runs as the contract check.
12. **Unit tests use explicit config values, never the local `.env`; the real configured values are checked by `scripts/check_env.py`.** Tests must give the same result on every machine.
13. **Orion "current budget" prompt is left unchanged after the first real run answered 5M instead of 4.2M.** One run is anecdote; measure the failure rate with repeats in the eval phase before changing the prompt.
14. **Supersession is explicit (`supersedes: <id>`) and checked on load: same or stricter access, strictly later effective date.** A public v2 of a restricted doc would leak it; an unordered pair has no "current" version. Explicit field over a `-v2` naming convention.
15. **Retrieval index cached on disk (`.cache/`), keyed by sha256 of embedding model + exact doc texts.** Re-embedding took ~6 s per CLI call; any doc edit or model change yields a new key, so a stale index is never reused. The cache holds vectors of restricted docs too, so it stays out of git.
16. **Access-filter tests carry `@pytest.mark.security` but stay in `tests/unit/`.** `pytest -m security` selects them without moving files; they use FakeLLM and real retrieval as the security rules require.
17. **Tests that pass for the wrong reason get a mutation check before they count.** A green test only has signal if some plausible bug turns it red. Four found in review rounds 2-3, each fixed and then proven by breaking the code on purpose:
    - *Vacuous `all()`*: `all(public for h in hits)` passes on `[]`, which is exactly what filter-after-top-k returns at k=1. Fix: assert `len(hits) == 1` too, plus the precondition that the restricted doc ranks first for the lead. Mutation "filter after top-k" -> `test_top1_for_restricted_best_match_is_one_public_doc` fails.
    - *Control that can't see its bug*: the `num_ctx=256` budget control passed on fixed prompt parts alone, even if docs were never counted. Fix: add a 30k-char restricted doc and assert the estimate grows by it. Mutation "estimate ignores docs" -> `test_estimate_counts_restricted_docs` fails.
    - *Assertion already enforced upstream*: "v2 is dated later" could never fail because the loader raises first; the real gap was a `-v2` doc without `supersedes`, which skips the check. Fix: assert every `-vN` doc declares `supersedes`. Mutation "drop `supersedes` from holiday-policy-v2" -> `test_every_versioned_corpus_doc_declares_what_it_supersedes` fails.
    - *Negative test that passes on empty input*: "`_TEMPLATE` is skipped" passed if the loader returned nothing; "rejected" tests matched only the file name, so any error passed. Fix: assert the fixture ids still load; match the rejection reason. Mutations "loader returns []" and "unknown target reported as a date problem" -> `test_loader_skips_underscore_files` and `...cannot_be_ordered_is_rejected[unknown-target]` fail.

    Also proven by mutation: dropping the model from the cache key, and not sending `num_ctx` to Ollama, each fail one targeted test. A first draft of the last mutation kept the text "unknown id" and survived -- the mutation, not the test, was wrong; mutations must remove the behaviour, not reword it.
18. **Traces of a call that retrieved any restricted doc mask the question, prompt and every model output; structure stays visible.** Kept: doc ids, access levels, scores, token counts, durations, attempts, error, refusal_reason, truncation_risk, model, user id. Safer: restricted text never leaves the process, not even to our own Langfuse project, which has wider access and longer retention than the docs. Cost: a wrong answer on a restricted question cannot be read in the Langfuse UI; debug it by re-running the question locally with the CLI as `lead`. Details:
    - Decided on *retrieved* docs, not cited ones: everything retrieved is in the prompt, and a model can leak a figure from a doc it does not cite.
    - Decided in our code before the SDK sees anything, not with Langfuse's `mask` hook: that hook sees one value at a time and cannot know what this call retrieved. `mask_otel_spans` could, but adds a second mechanism; the security test already checks the full OTel export.
    - Mask shows length only. No hash (a short answer like "4.2 million euros" is brute-forceable by hashing guesses), no prefix (the first words are often the secret).
    - Fail closed: until retrieval reports its hits, a call counts as restricted.
19. **The eval runner does not use the SDK's `run_experiment`.** It writes each item's input and expected output onto its own spans unmasked, which would bypass #18, and it runs task and evaluators in one pass. Instead each answer's own masked trace is linked with `api.dataset_run_items.create`, and scores are added later with `create_score` and a deterministic `score_id` (sha of trace id + score name), so re-running the judge overwrites instead of duplicating.
20. **Expected and forbidden facts never go to Langfuse.** For restricted items they ARE the restricted text. Uploaded per item: question, user, category, should_refuse, as_of. Code evaluators refer to facts by position ("missing #2") because their details become score comments; the judge's reason can quote the answer, so it is masked exactly like the trace. Cost: the Langfuse UI cannot show expected facts next to an output; the local results file and report can. Questions are uploaded as-is; the validator rejects a question that contains one of its own facts.
21. **Two passes: generate, then evaluate.** Only one large model is in memory at a time (gen model unloaded after pass 1; everything but the judge unloaded before pass 2), and the judge can be re-run without regenerating. The results file is rewritten atomically after every answer; `--resume` continues a crashed run and refuses a changed config.
22. **Two dataset hashes.** `generation_key` covers what answers depend on (ids, questions, users, dates); `sha256` covers the whole file including facts. Fixing a fact typo re-grades saved answers; changing a question or date requires regeneration. `compare` refuses runs graded against different facts.
23. **The dataset has a fixed `as_of` date** (header default, optional per-item override) instead of the real date. The Orion trap flips on 2027-01-01; with the wall clock, the same run would change verdict over time. Recorded in results; `compare` refuses runs with different `as_of`.
24. **Run config records Ollama model digests, not only tags.** `qwen3:4b` points to whatever was last pulled; the digest identifies the weights.
25. **Evaluators are an independent oracle.** `citations_valid` parses the model's own final output and checks it against corpus access and users.yaml; it does not trust `result.error`. An app bug must not hide itself in the evals.
26. **A fact is a string or a list of accepted variants; `facts_recall` passes only at 1.0 (all facts).** The first variant is canonical and must appear verbatim in the corpus (checked in code), so no fact is unsatisfiable by typo. Matching is casefold + whitespace-collapsed substring; no number normalization, so spellings like "4,2 million" are listed as variants.
27. **`evals/dataset.draft.jsonl` was generated by Claude, not written by Marko.** 30 items (factual 8, multi_doc 5, unanswerable 5, restricted_probe 6, injection 2, versioning 4) to build and smoke-test the pipeline. It will be compared with Marko's hand-written `evals/dataset.jsonl`: a generated set shares the generator's blind spots (question style, what counts as a fact), so its numbers are not the project's results.
28. **The judge gets the item's `as_of` date, the documents' effective dates, and the rule "use the latest version in force on as_of".** In smoke run `20260925-smoke-draft` it failed correct answers ver-02 (score 2) and ver-03 (score 3) as "context has conflicting versions": it saw both versions without dates and could not tell which one was in force. Negative control: a not-yet-effective Orion figure for an as_of before v2 must score below the pass threshold, so the fix cannot turn into "accept either version".
    - **Prediction, written before the change:** re-running only `evaluate` on `20260925-smoke-draft`, ver-02 and ver-03 flip to pass, nothing else changes.
    - Known risk, recorded in advance: the judge runs at Ollama's default temperature, so a flip on another item may be judge noise rather than the prompt change. Any such flip is reported, not explained away.
    - **Outcome: prediction held only in part.** ver-03 flipped to pass (judge 3 -> 5). ver-02 did NOT flip (judge 2 -> 2; 2 in 5 of 5 re-samples, so systematic, not noise). Its reason works out that 5 million is in force on 2027-03-01, then scores 2 anyway: the JSON puts `score` before `reason`, so the score is emitted before the reasoning. Other change: fact-01 judge 5 -> 4, still a judge pass; the item fails on `facts_recall` either way. Item pass count 24 -> 25 of 30. The negative and positive controls only cover an as_of BEFORE Orion v2; the failing side (as_of after v2, new figure correct) had no control. Proposed next step, not done: reason before score in the judge schema, plus a control for the after-v2 side, with its own prediction.
29. **`expected_docs` per item and a `retrieval_recall` evaluator that is diagnostic, not gating.** It splits a failed answer into a retrieval miss (expected doc never in the context) and a generation failure (doc there, not used). Not gating because a fact can live in several docs ("Roster app" is in seven) and the user sees the answer, not the ranking; a miss must explain failures, not create them. `EvalResult.gating=False` marks it; `answer_passed` and the report's failing list skip it. Expected docs must be readable by the item's user (checked in code): expecting a restricted doc for the analyst would reward a leak. Versioned policies expect the version in force on as_of. Optional in the schema; the draft set fills it for every answerable item.
30. **Judge v3: `reason` before `score` in the judge's JSON, plus a control pair for an as_of after Orion v2.** Structured outputs decode fields in schema order, so with `score` first the judge commits to a number before writing any reasoning (DECISIONS #28, ver-02). The new controls cover the side that failed: as_of after 2027-01-01, where 5 million is in force and 4.2 million is superseded.
    - **Prediction, written before the change:** re-running only `evaluate` on `20260925-smoke-draft` (same answers, same judge model):
      - ver-02 flips to pass (judge 2 -> 4 or 5), and scores >= 4 in 5 of 5 re-samples. Its v2 reason already concluded 5 million is in force; with the reason emitted first, the score is conditioned on it.
      - No other item changes pass/fail: item pass count 25 -> 26 of 30. Every other judged answer stays >= 4 (fact-01 may move between 4 and 5).
      - Controls, 3 samples each, all agree: before v2, 5 million fails and 4.2 million passes (unchanged); after v2, 5 million passes and 4.2 million presented as current fails.
    - Known risk, recorded in advance: reasoning first gives the judge room to find "unsupported" minor details, so it may get stricter on answers it now scores 4-5 (multi_doc most likely). The judge still samples at Ollama's default temperature with one sample per answer in the run. Any flip is reported as a prediction miss, not explained away.
    - **Outcome: the run held, the controls did not.** Judge v3 = prompt `ad47ba4fb182` (v2 was `797638a132e2`).
      - Run, as predicted: ver-02 flipped to pass (judge 2 -> 5), 5 of 5 re-samples scored 5. Item pass count 25 -> 26 of 30; no other item changed pass/fail. Score-only changes: fact-01 4 -> 5 (allowed by the prediction; still fails `facts_recall`), ver-03 4 -> 5 (not predicted; was already a pass). No item got stricter.
      - Controls, NOT as predicted. Before v2: both still hold (3 of 3). After v2: *4.2 million presented as current* scored 5 in 3 of 3 in pytest and 3 of 3 in a re-sample, so the negative control fails; *5 million* failed at least 1 of 3 in pytest and scored 1 in 1 of 8 re-samples. Every wrong verdict has the same cause in its reason: the judge misorders the dates ("2027-01-01 ... is not yet in force as of 2027-03-01"). qwen3:4b does not compare ISO dates reliably.
      - Not caused by v3: with the v2 prompt, 4.2 million after v2 also scored 5 in 5 of 5, and 5 million after v2 scored 2 in 3 of 3 (one more sample timed out twice at 300 s). v3 fixed the positive side (mostly) and left the negative side as lenient as it was.
      - What still catches a wrong version: `forbidden_absent`, a code evaluator (ver-02 forbids "4.2 million"). The judge alone cannot be trusted to enforce the version in force after an effective date has passed.
      - Cost noticed: reasons are much longer with reasoning first (several contain "But wait, ..." loops). The 30-answer evaluate took ~50 min on CPU; long replies are a timeout risk.
      - The two after-v2 controls stay failing; they measure a real judge weakness. Proposed next step, not done: decide the version in force in code (DECISIONS #6 already defines it) and label each document in the judge prompt as in force / superseded / not yet in force, so the judge no longer compares dates. Needs its own prediction.
31. **Evaluations are stored per judge prompt version (first 12 hex of its sha256; `no-judge` without a judge).** Re-running the same judge prompt overwrites its own evaluation; a new prompt is stored next to the old one, so a judge change can be compared on the same answers. Reports use the latest evaluation; `stats report --judge <prefix>` picks another. Results files with the older single `evaluation` load under their judge's key.
    - Langfuse score ids follow the same rule, but only for scores that depend on the judge (`judge_faithfulness`, `item_pass`); they also carry `metadata.judge`. Code evaluator scores keep one id per trace and name: they do not depend on the judge, and one copy per judge version would only duplicate them.
    - Cost: Langfuse shows each judge version's `judge_faithfulness` as another score with the same name on the same trace, and aggregate views average them. Filter by `metadata.judge` in the UI; the local report is per version.
    - Scores sent before this change used the old id (trace + name). The judge v3 re-run overwrote v2's judge scores in Langfuse under that old id; they stay there until evaluate runs again, which then adds v3 scores under the new id next to them.
32. **`evaluate` saves after every graded answer and can `--resume`; a judge timeout is retried once, then becomes a `judge_error`.** The v3 re-run took ~50 min and a judge call can hang for minutes (one real sample timed out twice at 300 s); before, one timeout aborted the pass and only the end of it was saved.
    - An evaluation has `finished_at`; reports and `compare` refuse an unfinished one, because rates over some of the answers look like rates over all of them.
    - `--resume` continues only an unfinished evaluation by the same judge (prompt, model, digest) against the same facts; mixing grades from two judges would measure neither. Without `--resume`, a resumable evaluation is not thrown away by accident (refused); one that can no longer be resumed is replaced.
    - The Ollama read timeout is `OLLAMA_READ_TIMEOUT_S` (default 120; connect stays at 10 s). The client turns an httpx timeout into `LLMTimeoutError`, so the judge does not depend on httpx and FakeLLM can raise it in tests. Every failed judge attempt is kept in `attempt_errors`; the report counts timeouts including those whose retry succeeded, since they show the timeout is too tight before they become errors.
    - A timeout during generation still stops `generate`; it already saves after every answer and has `--resume`.
    - "Latest evaluation" is the one written last (dict order), not the latest `evaluated_at`: two evaluations written within one Windows clock tick (~15 ms) had equal timestamps and a unit test picked the wrong one.
33. **Hypothesis before judge v4: the judge misorders dates only when both dates are in the same year.** In #30 every wrong verdict compared 2027-01-01 with an as_of of 2027-03-01; the holiday and remote-work versions (2025-01-01 vs 2026-06-01, a different year) were graded correctly in the smoke run. Test it on the current judge v3 (`ad47ba4fb182`), unchanged, with a new control pair at as_of 2028-03-01: 5 million presented as current must pass, 4.2 million presented as current must fail. 10 samples per case, not 3: at 3 a judge that is wrong 20% of the time still passes a control about half the time.
    - **Prediction, written before the run:** if the hypothesis holds, both 2028 controls agree in 10 of 10 samples on v3, while the 2027-03-01 pair keeps failing as in #30. The hypothesis is falsified if either 2028 case is wrong in 2 or more of 10 samples. 1 of 10 is reported as inconclusive (the 2027 side was wrong in only 1 of 8 re-samples on the positive case).
    - **Confound, recorded in advance:** the 2028 pair differs from the failing 2027-03-01 pair in two ways at once, the year and the gap to the effective date (14 months vs 2). A pass supports "different year OR larger gap", not "same year" alone. Separating them would need a same-year control with a large gap (e.g. an effective date early in a year and as_of late in it), which the corpus does not have for Orion; not added now.
    - Whatever the outcome, v4 still moves the date comparison into code: a judge that is right only for some date pairs cannot be trusted on a dataset whose as_of Marko chooses.
    - **Outcome: hypothesis falsified.** v3 (`ad47ba4fb182`), 10 samples per case, as_of 2028-03-01:
      - *5 million presented as current* (should pass): 9 of 10 passed (score 5); 1 scored 1. The wrong one did not misorder dates: it concluded that "the budget for 2028-03-01 is not provided" because the document gives no later version. 1 of 10 is inconclusive by the rule above.
      - *4.2 million presented as current* (should fail): **7 of 10 wrongly passed** (score 5), 3 failed as they should (score 1; one after a timeout and retry). Six of the seven wrong reasons misorder the dates exactly as in #30, now across years: "the second document (effective 2027-01-01) is not yet in force (it's effective after AS OF)" with AS OF 2028-03-01. The seventh reads the v2 body ("Until then the current budget remains in force") as keeping the old budget in force.
      - So the date errors are not limited to same-year pairs, and a 14-month gap does not help; the confound does not matter because neither variable rescued it. The negative side (superseded value presented as current) is the weak side on both dates.
      - The two 2028 eval controls fail on v3, as the two 2027-03-01 ones do. Durations: 16-77 s for the passing case, 35-161 s for the failing one (one timeout).
      - Consequence for v4: move the date comparison into code, as planned. The controls then test whether the judge follows the labels.
34. **Judge v4: the version in force is decided in code and labelled in the judge prompt.** `evals.judge.version_status` computes, for each document in a `supersedes` chain, its status on the item's as_of: *in force*, *superseded* or *not yet in force*. The judge prompt shows it next to the effective date (`status on AS OF: superseded`) and the rubric says to use the labels as given instead of working the status out from the dates. Docs outside a chain get no label. The function is written in the evals package from the document data, not taken from the app (#25): if the app picked the wrong version, the judge must not inherit the bug. Status is computed over the whole corpus, since the version that replaces a retrieved doc may not have been retrieved.
    - **What the controls measure changes.** With labels, the Orion controls test whether the judge *follows the labels*, not whether it can compare dates. Date comparison is now tested by unit tests of `version_status` (same year, different year, the effective day itself, a chain of three), which are deterministic. A future judge without labels would need the date-comparison controls back.
    - **Prediction, written before the change** (same judge model, same answers):
      - Controls: all 6 pass, every sample: before-v2 pair 3 of 3 each, 2027-03-01 pair 3 of 3 each, 2028-03-01 pair 10 of 10 each.
      - Smoke run `20260925-smoke-draft`, re-running only `evaluate`: item pass count stays 26 of 30, no item changes pass/fail. The labels also appear on the holiday and remote-work docs; those answers were already graded correctly and stay >= 4.
    - Known risks, recorded in advance: (1) the judge may still override a label with its own date reasoning, or with the v2 text "Until then the current budget remains in force" (one v3 sample already read it that way); (2) a label is new text the judge can treat as a claim to check, making it stricter on answers that do not mention versions. Any change is reported as a prediction miss, not explained away. The judge still samples at the default temperature.
    - The judge's duration and output tokens are now recorded per answer, so this run is the "before" for the judge-cost change.
    - **Outcome: prediction held on the run, missed on the controls.** Judge v4 = prompt `be5839e523ff`.
      - Smoke run, as predicted: item pass count 26 of 30, no item changed pass/fail and no judge score changed (all 21 judged answers score the same as on v3).
      - Controls, 2 rounds (a sampling script with reasons, then pytest), wrong verdicts / samples:

        | case | v3 (#30, #33) | v4 |
        |---|---|---|
        | before v2, 5M current (fail) | 0/3 | 0/6 |
        | before v2, 4.2M current (pass) | 0/3 | 0/6 |
        | 2027-03-01, 5M current (pass) | >=1/3, 1/8 | 0/6 |
        | 2027-03-01, 4.2M current (fail) | 3/3, 8/8 | **1/6** |
        | 2028-03-01, 5M current (pass) | 1/10 | 0/20 |
        | 2028-03-01, 4.2M current (fail) | 7/10 | **3/20** |

        The labels fixed the positive side completely and cut the negative side from mostly wrong to 4 wrong in 26. pytest: 5 passed, 1 failed (2027-03-01 4.2M scored `[5, 1, 1]`); the 2028 pair passed 10/10 in that round.
      - The wrong reasons override the labels, as risk (1) said: "matches the superseded version ... Since the AS OF date is 2028-03-01, the revised budget (in force) is already past its effective date, so the superseded version remains the current one". The judge reads the labels and still reasons from dates.
      - The judge alone still cannot be trusted to fail a superseded value presented as current (~15% lenient). `forbidden_absent` stays the check that catches it. The failing control stays failing; it measures a real judge weakness.
      - Cost: the "But wait" loops are gone with the labels. Smoke run judge p50 47.8 s, p95 59.2 s, output tokens p50 79, p95 101, max 110; controls output tokens p50 138, p95 205, max 236 (the negative Orion case writes the longest reasons). No timeouts.
      - Not done, proposed: the lenient 4.2M verdicts all come with the "superseded" label in context, so a next step could be a code check in the judge's place for version items (answer quotes a value only found in a non-in-force doc -> fail), which is what `forbidden_absent` already does with dataset facts. Marko to decide.
35. **Judge v5: reason at most 3 sentences, output capped at 256 tokens (`num_predict`).** v3 reasons ran into "But wait, ..." loops and the 30-answer evaluate took ~50 min; a runaway reply is also the main timeout risk. The cap is part of the judge version (evaluation key `<prompt sha>-np256`, DECISIONS #31), and a reply cut off at the cap is a failed attempt (`truncated`: one retry, then `judge_error`), counted in the report, never graded.
    - **How the cap was chosen, measured before this prediction:** the 3-sentence rule alone (prompt `3870776dcad7`, no cap) on the controls, 32 samples: output tokens p50 112, p95 162, **max 195**; duration p50 35.4 s, p95 57.9 s; one timeout, retried. Cap = 256, about max + 30%, rounded. For comparison v4 (`be5839e523ff`): controls p50 138 / p95 205 / max 236 tokens; smoke run p50 79 / p95 101 / max 110 tokens, duration p50 47.8 s, p95 59.2 s.
    - The measurement also showed a verdict change not asked for: with the 3-sentence rule the controls were right in 32 of 32 samples (v4: 4 wrong of 26 on the superseded-4.2M cases). Recorded here because it shapes the prediction; 10 samples per case is still small.
    - **Prediction, written before running evaluate** (judge v5 = prompt with the rule + cap 256):
      - Smoke run `20260925-smoke-draft`: pass/fail identical to v4, 26 of 30; 0 replies cut at the cap; 0 judge errors.
      - Judge duration on the smoke run: p50 at most 45 s, p95 at most 59 s, i.e. only a small drop. v4's smoke reasons were already short (max 110 tokens), so on CPU the prompt, not the reply, dominates; the big cost cut came with the v4 labels, not with this change. The cap is a guard against runaway replies more than a speed-up.
      - Controls (pytest, with the cap): 6 of 6 pass.
    - Known risks: a cap well above every measured reply should never bind, but a single "But wait" loop would now become `truncated` instead of a slow answer; if that happens it is counted, not raised. The judge still samples at the default temperature.
    - **Outcome: verdicts as predicted, cost prediction missed.** Judge v5 = `3870776dcad7-np256`.
      - Smoke run: pass/fail identical to v4, 26 of 30, every judge score the same as v4; 0 judge errors. Controls in pytest: 6 of 6 passed (v4 round: 5 of 6).
      - **Missed: 1 reply was cut at the cap** (predicted 0). ver-02's first attempt ran past 256 tokens; the retry scored 5 in 136 tokens. The runaway reply the cap guards against does still happen; it cost one retry (133 s for that answer) instead of an unbounded reply.
      - **Missed: the judge got slower, not faster.** Duration p50 47.8 -> 57.7 s, p95 59.2 -> 70.2 s (predicted p50 <= 45, p95 <= 59). Output tokens went up too: p50 79 -> 99, p95 101 -> 134, max 110 -> 136. On the smoke answers the v4 reasons were already shorter than 3 sentences; "name the claim and the document" made them longer. Confound, recorded: I ran unit tests and mutation checks (a few seconds each) on the same CPU during this run, which can add some seconds; it cannot explain the token increase.
      - So the 3-sentence rule is not a cost fix on this data. What cut cost was v4's labels (no more "But wait" loops). What v5 adds: a hard bound on a runaway reply (now counted as `truncated`), and on the controls the rule coincided with 32 of 32 correct verdicts plus 6 of 6 in pytest, against 4 wrong of 26 on v4's negative cases. That verdict gain is 2 rounds of samples, not proven; keep the controls running on every judge change.
      - Proposed, not done: keep v5 for its bound and control results, but do not claim a speed-up. If judge cost matters for Phase 4 repeats, measure where the time goes (prompt eval vs reply) from Ollama's `prompt_eval_duration` / `eval_duration` before changing anything else.
36. **Judge v5 (`3870776dcad7-np256`) is kept and frozen for Phase 4.** Marko's decision on 3.3. v5 is safer, not faster: the output cap bounds a runaway reply and a cut-off reply is detected (`truncated`, one retry, then `judge_error`), and the controls held 6 of 6 plus 32 of 32 samples. It did not cut cost: the 3-sentence rule made smoke-run replies longer than v4's (tokens p50 79 -> 99, duration p50 47.8 -> 57.7 s). No judge prompt change during Phase 4; a change would move the numbers Phase 4 measures.
37. **Version correctness stays with `forbidden_absent`; no more judge work on versioning before Phase 6.** Marko's decision on 3.3. The judge is still ~15% lenient on a superseded value presented as current on v4's controls (#34); a code check for version items in the judge's place is not built. `forbidden_absent` fails a wrong version from the dataset facts, independently of the judge. 38. **Phase 4 design: one frozen run with R repeats, judge noise measured apart, paired compare.** Marko's plan review, 2026-09-27 (plan in `_planning/plans/2026-09-27-phase-4-noise.md`).
    - **One run, R repeats, instead of 3 runs x 5.** Each repeat is already its own Langfuse dataset run (`<name>-r<n>`), so repeat-to-repeat is run-to-run. R from the smoke run's timing (gen p50 33.1 s / p95 43.3 s x 30 items; judge p50 57.7 s / p95 70.2 s x ~21 judged answers): R = 6 plus K = 3 re-judges = 4.7 h at p50, 5.9 h at p95. R = 7 would be 6.6 h at p95. At R = 6 an item with a true 10% fail rate shows a fail with probability 47%, so "stable" means "no other verdict seen in 6".
    - **Frozen config file** (`run_experiment freeze`, reviewed and committed by Marko; not a baseline, no thresholds). `generate|evaluate|rejudge --frozen` list every differing field and refuse. generate also checks the judge, so a mismatch fails at the start, not hours later at evaluate. The dataset view is the whole file, so a filtered dry run over the frozen dataset is allowed (the filter is recorded separately). Dataset path is ignored; the hashes decide.
    - **Dirty tree:** tracked changes (anything in `git status --porcelain` except `??`) refuse, because evaluator and parsing code is not hashed into the config; untracked files only warn. `results/` (including the night-run log) is gitignored, so the run never dirties the tree.
    - **Judge samples are stored next to the evaluation, never over it, and stay local.** Sending them to Langfuse would either overwrite the main judge score (deterministic score ids) or clutter the dataset-run view with extra names. `--resume` continues and extends; without it existing samples are refused. A different judge digest is refused: two judge builds would show up as judge noise.
    - **Wilson over items with fractional successes** (sum of item rates, n = items). Treats each item as one trial; conservative, since a mean of fractions varies less than p(1-p)/n.
    - **Split distribution is unsigned:** a split into two groups has no baseline side, so |delta| is reported and the "worst drop" is max |delta| (Marko's review). With R = 6 there are only 15 / 45 / 10 splits for g = 1 / 2 / 3, so the max is rough.
    - **Paired bootstrap in compare:** resample items with replacement, 10000 times, seed 0 (same file, same interval). Paired because item difficulty varies far more than the changes we look for. No per-category interval: 2-8 items.
    - **Safety evaluators under no change** (`forbidden_absent`, `citations_valid`, `refusal_correct` where a refusal was expected) are counted per repeat. Phase 5's zero tolerance is only workable if this is 0; if not, Marko decides.
    - **Langfuse never fails a run** (Marko's review). Dataset upload and run links are synchronous API calls: an error is caught, logged, stored in the results file and shown by `report`; `run_experiment publish` re-sends failed links and ALL scores (scores are queued by the SDK, which only logs delivery errors after queueing; deterministic ids make a re-send an overwrite). Tested with the real SDK over a MockTransport answering 503 (the SDK's retry delay is set to 0 in that test for speed).
    - **`--resume` means "continue or start, never throw away"**: nothing stored -> start; unfinished -> continue; finished by the same judge and facts -> nothing to do; anything that would be replaced -> refuse. So `scripts/night_run.ps1` passes it to every step and a re-run after a crash picks up where it stopped. Each step is retried twice after 60 s (a crashed Ollama can come back), then the script stops.
    - **Proposed Phase 5 margin (Marko decides the numbers):** margin(g) = max(worst |delta| over the no-change splits of size g, half-width of the no-change paired bootstrap), rounded up to a whole point; choose g so the margin still catches one broken category (2-8 items of 30 = 7-27 points). Both already include judge noise (each repeat judged once); the rejudge numbers say how much of it is the judge.
